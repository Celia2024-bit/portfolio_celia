Side Project

Automated Crypto Trading System

GitHub → Toolkit Docs ↗
C++ / Python · Binance API · Docker · GitHub Actions

Built from scratch to push myself into real high-performance system design. Python pulls live market data from Binance, C++ makes the trading decisions. They're isolated over a socket — if Python crashes, the C++ engine keeps running. Inside C++, three dedicated threads communicate through thread-safe queues to keep everything predictable and fast.

But the part I'm most proud of is the engineering discipline around the system — the tooling, the automation, the CI/CD gate. The goal was simple: build a system where problems get caught automatically, before they ever reach production.

Manual instrumentation in C++ is a losing game — you clutter every function with logging and validation, and then you can never get it back out again. So I built one tool that does it at build time from the Clang AST rather than regex, and that can reverse itself: run the remove config and src/ comes back byte-for-byte identical.

// trace_injector.py · three injections, one AST pass

A JSON config says which directories to instrument, which to leave alone, and which of trace · validate · guard to apply. Every line it writes carries an // @autogen marker, and that marker — not the C++ on the line — is how removal recognises its own work. A hand-written ScopeTrace is left alone; the earlier regex-matching version deleted those too.

config_all_cases_inject.json
{
  "inject": [{
    "directory": "src",
    "inject_type": ["trace",
      "validate", "guard"]
  }],
  "exclude": [
    { "directory": "src/TradeStrategy" },
    { "directory": "src/Test" }
  ]
}
config_all_cases_remove.json · the undo
{
  "remove": [{
    "directory": "src",
    "inject_type": ["trace",
      "validate", "guard"]
  }]
}

# Removal is kind-blind: it strips
# every @autogen marker it finds,
# whatever inject_type wrote it.
BEFORE · original source
bool TradeExecutor::ExecuteBuyOrder(
  double price, double amount)
{
  // business logic
  return placeOrder(price, amount);
}
AFTER · trace + validate + guard
bool TradeExecutor::ExecuteBuyOrder(
  double price, double amount)
{
  ScopeTrace trace(         // @autogen: trace
    __FILE__, __LINE__,     // @autogen: trace
    "TradeExecutor::ExecuteBuyOrder"
  );                        // @autogen: trace

  static const char* __param_names[]
    = { "price", "amount" };
  validate_params("...::ExecuteBuyOrder",
    __param_names, price, amount);
                         // @autogen: validate

  try
  {                        // @autogen: guard
    // Original body — untouched,
    // not even re-indented
  }
  catch (const std::exception& error)
  {
    ErrorLogger::LogError("TradeExecutor",
      "ExecuteBuyOrder", "std::exception",
      error.what());
    throw;      // @autogen: end of guard
  }
}
🔁 Reversible by construction
The guard is the hard case — it writes at both ends of the body, so its closing half carries a different marker (end of guard) and the remover can never mistake an opening for a closing.

The original body is not re-indented, even though it now sits one level shallower than the try around it. That is deliberate: reindenting would turn every injection into a diff across the whole function, and byte-identical removal is the entire promise.

throw; is not optional either — swallowing the exception would change what the program does, and in a function that returns a value it would run off the end of the body.
📐 Ordering is load-bearing
guard is applied last, so its try opens directly above the original body. That puts ScopeTrace and the parameter check outside the try — which is what you want:

the trace object is still alive while the catch runs, so its destructor logs the exit after the error is recorded. Reverse the order and the exit log vanishes from exactly the runs you care about.

Adding a fourth injection kind is one entry in INJECTION_KINDS; inject and remove both read from it, so the two cannot drift apart.
// ParameterCheck.h · what the injected validate call lands in

The injector only writes the call. The type dispatch behind it is a C++17 if constexpr chain in the util library — one compile-time branch covering every parameter type, with no runtime overhead and no specialisation boilerplate.

Inside validate_params() — the function the injected line calls:

⚡ if constexpr Dispatch
Resolved entirely at compile time — branches that do not apply are never emitted.

Floats: std::isfinite — catches the NaN from a bad division
Pointers: nullptr guard
Structs: calls the type's own isValid()
Containers: non-empty guard via empty()
Enums: check_traits<T> range gate — registered for ActionType, SymbolType and CustomerLogLevel
Integrals: accepted as-is. A price of 0 and a count of -1 are each legitimate somewhere, so the check makes no assumption it cannot justify.
🔒 Fail-Fast Design
Pass a type nobody prepared and it is a compile error, not a silent pass:

static_assert — "Type is NOT prepared for validation! Provide one of: isValid() const, empty(), or check_traits<T> specialization."

Three ways to make a type validatable, all opt-in, none of them touching the check itself. ActionSignal takes the first route, and its isValid() in turn calls check_traits<ActionType> — validation composes.

A second static_assert caps it at 10 parameters; a function that needs more has a design problem the injector should not paper over.

CI/CD Pipeline

A GitHub Actions pipeline that does not just compile the project. One job builds the toolchain image and pushes it to ghcr.io; the next runs inside that image, so what tests the code is byte-for-byte what was just published. Then every commit triggers a 2-minute live run against real Binance market data — the C++ engine trading while a monitor attached to its PID samples memory, threads, handles and context switches once a second, aggregating them into ~63 trend points and two PNG charts.

Then the gate. Four metrics, checked two ways each: against an absolute ceiling, and for upward slope by least-squares fit across the whole run. Any one of the eight failing exits non-zero — which fails the job, which blocks the merge. The ceilings are the observed baseline doubled, not guesses. Voluntary context switches are plotted but deliberately not slope-gated: a thread yielding while it waits on a socket is this system working correctly, and gating on it would fail every I/O-bound build.

A 2-minute run is the point. A test that finishes in 40 ms cannot see a handle that is never released — it has no slope to look at. And artifacts upload on if: always(), so when the gate does block something, the chart explaining why is attached to the run that failed rather than waiting to be reproduced on someone's laptop.
