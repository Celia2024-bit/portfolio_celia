Real-time Performance Monitor

Python · JavaScript · Docker · Vercel · GitHub Actions

This tool came from a frustration I kept running into. In my own C++ trading system and on the IEC 61850 platform at work, some of the worst bugs are completely silent — they don't crash anything right away. Memory creeps up, thread count grows, handles never get released. Hours later the system falls over, and you have no idea why. Happy path tests are too short to catch this. They run for a few seconds and move on.

The key insight: watch the trend, not just the threshold. A slope is a problem. So I built a monitor that samples memory, thread count, handle count, and context switches every N seconds — aggregates them into trend points — then runs linear regression to detect upward slope. Integrated into CI/CD, if any metric shows a statistically significant upward trend, the pipeline automatically blocks the merge.

I also wanted it to be zero-friction for the team — there's a live web dashboard where anyone can check real-time system health just by opening a link. No setup, no SSH, no tooling.

Why these metrics? ↓
Voluntary context switches
A thread yields the CPU itself — waiting on a lock, a socket, or a condition variable. A rising voluntary rate means more lock contention or blocking I/O: threads are spending more time waiting for each other, even if CPU looks fine.
Involuntary context switches
The kernel forcibly preempts a thread because its time-slice expired. A rising involuntary rate means the system is genuinely CPU-saturated — more runnable work than cores to run it.
Why not just watch CPU%?
Instantaneous CPU% is too noisy. A 50 ms spike disappears between samples. A thread holding a mutex for 200 ms barely registers as CPU usage at all. The trend over time is what matters — a slow upward drift in voluntary switches reveals a contention problem long before throughput visibly degrades.
The Toolkit It Grew Into

The monitor was the first of these, not the only one. Working on the same C++ codebase kept turning up the same shape of problem — something mechanical, repetitive and easy to get subtly wrong by hand — so it ended up as four tools sharing one rule: anything that edits your source code has to be able to put it back exactly as it was.

Trace Injector walks the Clang AST to add tracing, parameter validation and exception guards, then removes them again byte-for-byte. State Machine Toolkit generates C++17 state machines and Mermaid diagrams from one definition, so the diagram cannot drift from the code. Interface Sync scans the header tree to propagate a changed signature through every implementation. And the Performance Monitor above is the one that watches the result.
